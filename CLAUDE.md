# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- Build everything: `./gradlew build`
- Build/check a single module: `./gradlew :app:assembleDebug`, `./gradlew :designsystem:build`, `./gradlew :formbuilder:build`, `./gradlew :network:build`, `./gradlew :data:build`, `./gradlew :common:build`, `./gradlew :feature:leaddashboard:build`, `./gradlew :feature:acquisition:build`
- Run unit tests: `./gradlew test` (single module: `./gradlew :formbuilder:testDebugUnitTest`, single test: `./gradlew :formbuilder:testDebugUnitTest --tests "com.touhid.composeform.formbuilder.FormValidatorTest"`)
- Run instrumented tests (needs a device/emulator): `./gradlew :app:connectedDebugAndroidTest`
- Lint: `./gradlew lint` (per-module: `./gradlew :app:lintDebug`)
- Install and launch on a running emulator/device:
  ```
  adb install -r app/build/outputs/apk/debug/app-debug.apk
  adb shell am start -n com.touhid.composeform/.MainActivity
  ```

## Architecture

Eight-module Gradle project, no `build-logic`/convention-plugin infrastructure — each module's `build.gradle.kts` is configured directly (this is intentional; see below).

- **`:app`** — the application shell. `MainActivity.kt` (`@AndroidEntryPoint`) hosts a single `NavHost` with the app's real destinations — `home` (`home/DemoHomeScreen.kt`, the launcher picking between the demos below), `leadDashboard` (`:feature:leaddashboard` — see below), `acquisitionApprovalList`/`acquisitionApprovalDetail` (`:feature:acquisition` — see below), plus `form`/`picker` (the `flow` package's demo server-driven form flow, backed by `DemoFormApi`'s in-memory mock — not real network calls). `specificform/` is another `AppRepository`-backed screen/ViewModel pair, still in `:app`. `ComposeFormApplication.kt` is the `@HiltAndroidApp` entry point, and `di/` holds the Hilt modules `:app` owns to configure `:network` — base URL(s), debug-logging flag, token storage — per the deferral pattern described below. `:app` hosts Compose content and is **not permitted to depend on Material3 or Foundation directly** — see "Design system boundary" below — and is **not permitted to depend on Square's networking libraries directly** — see "Network boundary" below.
- **`:designsystem`** — an Android library module (namespace `com.touhid.composeform.designsystem`) owning all Material3-based UI. `:app` depends on it via `implementation(project(":designsystem"))`.
- **`:formbuilder`** — an Android library module (namespace `com.touhid.composeform.formbuilder`) that parses a JSON form schema (`kotlinx.serialization`) and renders it using `:designsystem`'s components. Also subject to the Material3-free boundary — it depends on `:designsystem` only, never Material3 directly.
- **`:network`** — an Android library module (namespace `com.touhid.composeform.network`) owning OkHttp/Retrofit and all raw API/network work — Retrofit service interfaces, request/response DTOs, interceptors, the safe-call layer. Deliberately has no notion of "the repository consumers should inject" — see "Data layer" below for that.
- **`:data`** — an Android library module (namespace `com.touhid.composeform.data`) owning the repository layer: `AppRepository`/`PaymentRepository`/`AnalyticsRepository`/`PartnerRepository`, one per `:network` base URL. `:app` depends on **both** `:network` (for the Hilt qualifier/`TokenProvider` contracts it must configure — base URL(s), token storage) and `:data` (for the repositories it actually calls) — see "Data layer" below for why the split exists and why `:app` keeps a direct `:network` dependency despite it.
- **`:common`** — an Android library module (namespace `com.touhid.composeform.common`) holding small Compose UI helpers used by more than one screen: `copyIconButton` (a "copy to clipboard" trailing-icon slot), `LazyListState.OnEndOfListReached` (the shared infinite-scroll pagination trigger), `ListEmptyState`. Exists because these are genuinely cross-feature — both `:feature:leaddashboard` and `:feature:acquisition` use them — so they can't live inside either one specifically; putting them in `:app` (as before either feature module existed) would have forced the feature modules to depend back on `:app`, which runs the dependency graph backwards. Depends only on `:designsystem` + Compose.
- **`:feature:leaddashboard`** — an Android library module (namespace `com.touhid.composeform.feature.leaddashboard`, nested under a `feature/` parent folder — see "Feature modules" below) holding the lead-dashboard screen end to end: `LeadDashboardScreen.kt`, `LeadDashboardViewModel.kt` (`@HiltViewModel`, injects `AppRepository`), `LeadDashboardModels.kt` (the screen-local `LeadStatusFilter` enum). `:app` depends on it and wires it into `MainActivity`'s `NavHost`; nothing depends on `:app`. See "Feature modules" below for what this demonstrates and depends on.
- **`:feature:acquisition`** — an Android library module (namespace `com.touhid.composeform.feature.acquisition`, the second module under `feature/`) holding the acquisition approval list + detail/decision flow end to end: `AcquisitionApprovalListScreen.kt`/`AcquisitionApprovalListViewModel.kt` and `AcquisitionApprovalDetailScreen.kt`/`AcquisitionApprovalDetailViewModel.kt` (both `@HiltViewModel`, injecting `AppRepository`). Also depends on Coil (`libs.coil.compose`) for `AsyncImage`, used by the detail screen — the only feature module or `:app` code that still needs it, so `:app`'s own `coil.compose` dependency was removed once this moved out. `:app` depends on it and wires both screens into `MainActivity`'s `NavHost`; nothing depends on `:app`. See "Feature modules" below.

### Design system boundary (important, easy to violate accidentally)

`:designsystem` depends on `androidx.compose.material3` and `androidx.compose.foundation` as `implementation` (not `api`). Neither `:app` nor `:formbuilder` declare either dependency themselves. This means Material3/Foundation classes are not on their compile classpaths at all — any `import androidx.compose.material3.*` added there will fail to compile. This is deliberate, compiler-enforced encapsulation: all UI must go through `:designsystem`'s wrapped components (`AppText`, `AppButton`, `AppScaffold`, etc.), never the raw Material3 APIs. (Foundation layout primitives — `Column`/`Row`/`Box`/`Modifier.padding` — are fine for any module to use directly; only Material3 is restricted. This includes `Image` — `androidx.compose.foundation.Image` (and Coil's `AsyncImage`, used by `:feature:acquisition`'s detail screen) is Foundation, not Material3, so any module can call it directly with no `AppImage` wrapper needed; `Icon` is the one that's Material3-gated and needs `AppIcon`.)

When a module needs a new Material3 primitive it doesn't have a wrapper for yet, add the wrapper to `:designsystem` rather than adding a direct dependency elsewhere.

### `:designsystem` internal structure

```
designsystem/src/main/java/com/touhid/composeform/designsystem/
├── theme/                  # Color.kt (incl. semantic Status*/Status*Container tones), Theme.kt (ComposeFormTheme),
│                            # Type.kt, Spacing.kt (AppSpacing)
└── components/
    ├── text/               # AppText + AppTextStyle enum + AppTextOverride (size/weight/color override),
    │                        # AppIconLabelValue (icon + value, or label caption stacked above value;
    │                        # AppIconPosition: Start/End/Top/Bottom decides which side the icon sits on;
    │                        # optional subValue renders a second, smaller/muted caption below the value;
    │                        # optional trailingIcon sits next to the value itself, e.g. a copy glyph)
    ├── button/             # AppButton, AppOutlinedButton (+ AppButtonStyle: Primary/Success/Danger,
    │                        # both with an optional leadingIcon slot), AppStepperButton
    ├── layout/             # AppScaffold (topBar + optional bottomBar slot + content), AppPullToRefreshBox
    │                        # (wraps Material3's pull-to-refresh; isRefreshing/onRefresh + a BoxScope content slot)
    ├── input/              # AppTextField (+ AppTextFieldType: Text/Number/Email/Password), AppSearchField
    │                        # (pill-shaped filled search bar - distinct from AppTextField; leadingIcon
    │                        # defaults to none, trailingIcon defaults to none, both nullable composable
    │                        # slots so either/both can be omitted entirely), AppCheckbox,
    │                        # AppRadioButton, AppSwitch, AppDropdown (+ AppDropdownOption),
    │                        # AppRadioToggleChip, AppRadioCheckCircle
    ├── icon/                # AppIcon (non-interactive), AppIconButton (clickable)
    └── surface/             # AppTopBar (+ AppTopBarAction, AppTopBarScrollBehavior), AppCard (optional
                             # topContent slot renders before the padded content column, flush with the
                             # card's own bounds/corners - for a full-bleed banner), AppHorizontalDivider,
                             # AppStatusBadge (+ AppStatusTone: Success/Warning/Error/Info/Neutral - always
                             # shows a status dot), AppChip (selectable pill for filter tabs - no dot,
                             # communicates selection rather than state), AppBottomActionBar (flat elevated
                             # bar for a screen's pinned bottom actions), AppBottomSheet (wraps
                             # ModalBottomSheet, scrollable ColumnScope content slot), AppSnackbar (wraps
                             # SnackbarHostState; showMessage returns AppSnackbarResult - Dismissed/
                             # ActionPerformed - so callers react to e.g. a "Retry" action without seeing
                             # the raw Material3 SnackbarResult), AppProgressDialog (blocking,
                             # non-dismissable spinner overlay - for a reload with existing content behind
                             # it worth protecting from interaction) and AppProgressIndicator (a plain
                             # non-blocking inline spinner - for a screen's very first load, before there's
                             # any content yet)
```

Components are organized by category (not a flat package) — when adding a new component, put it under the matching category subpackage, creating a new one if it doesn't fit an existing one.

Conventions established by existing components:
- Each component wraps a Material3 equivalent with a narrowed, opinionated API (e.g. `AppTextStyle` enum instead of raw `TextStyle` passthrough) — don't leak Material3/Foundation types (like `PaddingValues`) through a component's public signature if avoidable (see `AppScaffold`: it absorbs `innerPadding` internally via a `Box` rather than exposing it). A container component's `content` slot should still be typed with that container's actual scope (`AppCard`'s is `ColumnScope`, `AppBottomActionBar`'s is `RowScope`, `AppScaffold`'s is `BoxScope`) — the scope isn't a Material3/Foundation type worth hiding, and exposing the wrong one (or none) either silently breaks `weight`/`align` modifiers at runtime or blocks them outright.
- Every component that renders text accepts an optional `AppTextOverride` (`fontSize`/`fontWeight`/`color`, all no-op by default) — `AppText`'s `override`, `AppButton`/`AppOutlinedButton`'s `textOverride`, `AppCheckbox`/`AppRadioButton`/`AppSwitch`/`AppDropdown`'s `labelOverride`. This is how callers (like `:formbuilder`) apply per-instance styling without the design system losing its opinionated defaults.
- Spacing between elements inside a component uses `AppSpacing` (`theme/Spacing.kt`) tokens, not hardcoded `dp` values.
- Each category subpackage has its own `*Previews.kt` file (not one global previews file) with a private composable carrying stacked `@Preview(name = "Light", ...)` / `@Preview(name = "Dark", uiMode = Configuration.UI_MODE_NIGHT_YES, ...)` annotations, wrapped in `ComposeFormTheme`.
- Modules outside `:designsystem` (e.g. `:app`) can reference `ImageVector` constants from `androidx.compose.material:material-icons-core` (or its superset, `material-icons-extended` — `:app` uses the extended artifact since it needs glyphs like `ContentCopy` outside the curated core set; both are separate artifacts with no Material3 dependency) directly and pass them into a designsystem component (`AppIcon`, `AppIconButton`, `AppTopBarAction`, `AppButton`'s `leadingIcon` slot, etc.) — but any `@Composable` slot lambda a caller *writes* (e.g. `AppIconLabelValue`'s `icon` param) still compiles as part of that caller's own module, so its body must only call designsystem-exposed composables (`AppIcon`, not raw Material3 `Icon`), never Material3 directly.
- Not everything a screen renders belongs in `:designsystem`, even when it's visually involved and looks reusable in principle. The boundary's purpose is specifically wrapping Material3 access `:app`/`:formbuilder` can't otherwise reach — a composition already buildable from exposed primitives (`AppText`, `AppIcon`, Foundation `Row`/`Column`/`Box`/`border`/`background`) has no Material3-wrapping reason to move, and "some other screen might want this shape someday" isn't a reason either - that's the same speculative-reuse trap the rest of this doc argues against for ordinary code. Ask two concrete questions instead of a hypothetical one: (1) does it have an *actual* second caller today, not an imagined future one? (2) does it use a Material3-derived default (`MaterialTheme.colorScheme...`) that its real caller(s) actually rely on, rather than always overriding? `AcquisitionApprovalDetailScreen`'s score-band step indicator and its score circle both answer no to both - one caller, always-explicit colors - so both live in `:app`, built from `AppText`/`AppIcon`/`AppTextOverride` plus plain Foundation shapes.

**Not yet built**: a generic Material3 `AlertDialog` wrapper (title/message/confirm-cancel buttons) — `AppProgressDialog` (spinner-only) and `AppBottomSheet` (modal bottom sheet) exist and cover their own specific cases, but nothing wraps a plain confirm/alert dialog yet. Follow the same wrapping conventions above when implementing it.

### Network boundary (same pattern as the design system boundary)

`:network` depends on `okio`, `okhttp` (+ `logging-interceptor`), and `retrofit2` (+ `converter-scalars`, `converter-gson`, `adapter-rxjava2`) as `implementation` (not `api`). `:app` does not declare any of these itself, so `okhttp3.*`/`retrofit2.*`/`okio.*` are not on its compile classpath — importing them there fails to compile. All API/network work (Retrofit service interfaces, request/response handling) belongs inside `:network`; the repository layer that's the actual thing `:app` calls lives in `:data` instead — see "Data layer" below.

`:network` is organized into subpackages by category, the same spirit as `:designsystem`'s: `api/` (Retrofit service interfaces), `model/` (request/response data classes), `auth/` (`TokenProvider`/`AuthInterceptor`, kept together since they're auth-domain-specific rather than grouped by "interceptor" shape), `interceptor/` (the other, non-auth, non-mock interceptors — currently `HeaderInterceptor`/`RequestIdInterceptor`), `mock/` (`MockDataInterceptor`/`MockJson` — split out from `interceptor/` since they're temporary scaffolding for the still-nonexistent backend, not a permanent interceptor, and the whole package gets deleted together once a real backend exists), and `qualifier/` (every Hilt qualifier — the four `@XBaseUrl`s plus the internal `@XRetrofit`s in `RetrofitQualifiers.kt`). `RetrofitFactory`, `NetworkModule`, `NetworkResult`/`NetworkError`, and `safeApiCall` stay at the package root since they're cross-cutting rather than belonging to one theme. There is no `repository/` package here — see "Data layer" below.

- `@BaseUrl` (`network/.../qualifier/BaseUrl.kt`) — a Hilt qualifier a consuming module's own Hilt module binds to a `String` (e.g. `@Provides @BaseUrl fun provideBaseUrl(): String = "..."`) so `:network` never hardcodes an environment's base URL. Retrofit requires a trailing slash (`https://api.example.com/`, not `.../com`) — `NetworkModule` normalizes a missing one, but supply it correctly regardless. Once product flavors exist, `:app` reads this from a per-flavor `BuildConfig.BASE_URL` — `:network` itself never needs to know about flavors. `:app` currently supplies a dummy URL via `di/AppNetworkModule.kt`.
- `AppApiService` (`network/.../api/AppApiService.kt`) — public (not `internal` — see "Data layer" below for why), the Retrofit service interface. Beyond `login`/`getManagerList`/`getAdminList`/`getAdminDetails`, it also backs the app's real screens: `getSpecificForm`, `getLeadDashboard` + `submitEkyc` (`:feature:leaddashboard`), and `getAcquisitionList`/`getAcquisitionDetail`/`getAcquisitionReasons`/`submitAcquisitionDecision` (`:feature:acquisition`). Bound as a Hilt-injectable singleton in `NetworkModule`. `:app` never references it directly (nothing in `:app` imports `network.api.*`) — by convention, not compiler enforcement, since `:app` does hold a direct `:network` dependency for other reasons (see below) — go through `:data`'s repositories instead, which is what actually enforces the safe-call/error-mapping and auth behavior.
- `network/.../model/` — the request/response data classes, Gson-reflected. The simplest (`LoginRequest`/`LoginResponse`, `ManagerSummary`, `AdminSummary`, `AdminDetails`) rely on exact field-name matching with no serialization annotations; ones mirroring a real backend's JSON shape 1:1 (`AcquisitionModels.kt`, `LeadDashboardModels.kt`, `SpecificFormModels.kt`, `LeadCloser.kt`) use `@SerializedName` for snake_case keys. Grouped one file per feature (e.g. all of an endpoint's request/response/nested types together), not one file per class. Screen-local UI types that aren't part of the wire format (e.g. `leaddashboard/LeadDashboardModels.kt`'s `LeadStatusFilter` enum) live in `:app` instead, despite the similar file name — never in `:network`.
- `NetworkResult`/`NetworkError` (`network/.../NetworkResult.kt`, `NetworkError.kt`) and `safeApiCall` (`network/.../SafeApiCall.kt`) — the safe-call layer, public so `:data`'s repositories can call it. `safeApiCall { ... }` runs a suspending Retrofit call on `Dispatchers.IO` and maps `HttpException`/`SocketTimeoutException`/`IOException`/anything else into `NetworkResult.Success`/`NetworkResult.Failure(NetworkError.Http|Timeout|NoConnection|Unexpected)` — `retrofit2`/`okhttp3`/`java.io` exception types never cross the `:network` boundary (into `:data` or `:app`), same spirit as not leaking Material3 types from `:designsystem`. `CancellationException` is rethrown, not wrapped.
- `network/.../auth/` — `TokenProvider` (the contract; storage is deferred to the consuming module, same pattern as `@BaseUrl`) and `AuthInterceptor` (`internal`, attaches `Authorization: Bearer <token>` when a token is present). `:app` binds `TokenProvider` to `di/EncryptedTokenProvider.kt` (backed by `androidx.security.crypto.EncryptedSharedPreferences`, so the token survives app relaunch) via `di/AppTokenModule.kt`. `:data`'s `AppRepository` also depends on `TokenProvider` directly (to store the token on a successful login), so `TokenProvider` stays public.
- `RetrofitFactory` (`network/.../RetrofitFactory.kt`) — `internal`, the one place that actually builds an `OkHttpClient`/`Retrofit` pair: `create(baseUrl, authInterceptor: Interceptor?, interceptors: List<Interceptor> = emptyList())`. Each base URL below calls it with exactly the interceptors that base URL needs — `authInterceptor` is nullable so a base URL that must never carry this app's bearer token (e.g. a third-party partner backend) omits it entirely rather than needing a per-method or per-client opt-out flag on an otherwise-shared client; `interceptors` covers anything else a given base URL needs (a static header, a bespoke error mapper) without every other base URL paying for it. Every base URL therefore gets its own `OkHttpClient` (its own connection pool), composed from this one shared factory rather than duplicating the timeout/mock-interceptor/logging boilerplate at each call site.
- `HeaderInterceptor` (`network/.../interceptor/HeaderInterceptor.kt`) — `internal`, takes a `Map<String, String>` and adds each as a header via `intercept`; the reusable way to give one base URL a static header (e.g. a partner's API key) by passing an instance into `RetrofitFactory.create()`'s `interceptors` list. Contrast with `RequestIdInterceptor` (`network/.../interceptor/RequestIdInterceptor.kt`) — a value that must be regenerated per request (an `X-Request-Id: UUID.randomUUID()`) can't be expressed as a fixed `HeaderInterceptor` map computed once at client-construction time; it needs its own `Interceptor` that generates the value inside `intercept()`. Since every base URL wants this (not per-client config the way an API key is), `RetrofitFactory.create()` adds it unconditionally rather than accepting it through the `interceptors` list.
- **Multiple base URLs**: beyond the main `@BaseUrl`/`AppApiService`/`AppRepository` trio, `:network` has three more base-URL-scoped API groups following the identical pattern — `@PaymentBaseUrl`/`PaymentApiService`/`PaymentRepository`, `@AnalyticsBaseUrl`/`AnalyticsApiService`/`AnalyticsRepository`, and `@PartnerBaseUrl`/`PartnerApiService`/`PartnerRepository` (placeholder names/endpoints for now; the `*ApiService`s live in `:network`, the `*Repository`s in `:data`). Each is its own Hilt qualifier (`network/.../qualifier/PaymentBaseUrl.kt` etc., public, bound by `:app`'s `AppNetworkModule`) plus an internal Retrofit-instance qualifier private to `NetworkModule` (`network/.../qualifier/RetrofitQualifiers.kt` — `@PaymentRetrofit`/`@AnalyticsRetrofit`/`@PartnerRetrofit`) used only to disambiguate the multiple `Retrofit` singletons from each other. `PartnerApiService`'s `Retrofit` is built with `authInterceptor = null` (its backend must never see our bearer token) plus a `HeaderInterceptor` carrying its own API key instead; `AnalyticsApiService`'s adds a `HeaderInterceptor` alongside its (non-null) `authInterceptor` to show the two composing together. Extending this further (a 5th base URL) means repeating this same shape: a public `@XBaseUrl` qualifier, an internal `@XRetrofit` qualifier, a public `XApiService` (`:network`), an `@Provides` pair in `NetworkModule` that calls `RetrofitFactory.create()` with whatever interceptors that base URL actually needs, and an `XRepository` (`:data`) — never reuse another group's `@BaseUrl`/qualifier for an unrelated backend.
- `NetworkModule` (`network/.../NetworkModule.kt`) — `internal`, provides the shared `HttpLoggingInterceptor` (debug-gated: `Level.BODY` only when `:network`'s own generated `BuildConfig.DEBUG` is true, `Level.NONE` otherwise so release builds never log request/response bodies) and, for every base URL above, a `@Provides` pair calling `RetrofitFactory.create(...)` for the `Retrofit` singleton and `retrofit.create(XApiService::class.java)` for the service singleton; not visible outside the module. `:network` enables `buildFeatures.buildConfig` itself for this — deliberately not a Hilt qualifier like `@BaseUrl`, since Gradle's variant-aware dependency resolution already gives every module the `BuildConfig.DEBUG` matching whichever build type of `:app` is being built, with no value needing to cross the module boundary.

### Data layer (`:data`)

`:data` holds the repository layer — `AppRepository`/`PaymentRepository`/`AnalyticsRepository`/`PartnerRepository`, one per `:network` base URL, each an **interface** directly in `data/.../repository/`. Its implementation (`AppRepositoryImpl`, etc.) lives one package deeper, in `data/.../repository/impl/` — a plain "interfaces at the package root, implementations in `impl/`" split, so `repository/` reads as the module's actual public contract at a glance. Each `*RepositoryImpl` is bound to its interface via `@Binds` in `data/.../di/RepositoryModule.kt` (`internal abstract class`, `@Module @InstallIn(SingletonComponent::class)`) — the interface/impl split exists purely for testability: a ViewModel test can substitute a fake implementing the interface without constructing a real `AppApiService`/`TokenProvider`, the same reason NIA declares its repositories as interfaces even though interface and implementation live in the same module. Consumers only ever reference the interface name (`AppRepository`, never `AppRepositoryImpl`) — Hilt resolves the binding. Each `*RepositoryImpl` wraps its `*ApiService` calls in `safeApiCall` (imported from `:network`, which stays the one place that maps `retrofit2`/`okhttp3` exceptions into `NetworkResult`); `AppRepositoryImpl` additionally stores the token via `TokenProvider` on a successful `login`, so callers never manage the token by hand — subsequent authenticated calls are authenticated for free. `AppRepository` is the one that's actually injected today: `LeadDashboardViewModel`, `AcquisitionApprovalListViewModel`, `AcquisitionApprovalDetailViewModel`, and `SpecificFormViewModel` (all `@HiltViewModel`) inject it directly.

This module exists as a deliberate split from `:network` — mirroring Google's "Now in Android" reference architecture, where `:core:network` (raw Retrofit/DTOs) and `:core:data` (repositories) are separate modules, and features depend on `:core:data`, never `:core:network`, directly. The consequence worth knowing: `AppApiService`/`PaymentApiService`/`AnalyticsApiService`/`PartnerApiService` had to become **public** (they were `internal` to `:network` before this split) — a repository's `@Inject constructor(apiService: XApiService)` is compiled inside `:data`, a separate compilation unit from `:network`, so `internal` can no longer hide the service interface from it. This is not a weaker boundary than before, it's the same one NIA itself relies on: the enforcement moves from "Kotlin `internal` visibility" to "the Gradle dependency graph" — nothing except `:data` has a reason to import `network.api.*`, and the actual invariant that matters (raw `retrofit2`/`okhttp3` types never reaching `:app`) is untouched, since those stay `implementation`-only inside `:network` regardless of this split.

`:app` keeps a **direct** dependency on `:network` in addition to its new `:data` dependency — this is intentional, not a leftover. `:app`'s own Hilt modules (`di/AppNetworkModule.kt`, `di/AppTokenModule.kt`) supply configuration *into* `:network` (base URL strings bound to `@BaseUrl` etc., `TokenProvider`'s implementation), which requires `:app` to see those qualifier annotations and the `TokenProvider` interface — a legitimate config-ownership relationship, independent of the repository/data-access boundary `:data` exists to enforce.

`:data` depends on `:network` via **`api`, not `implementation`** — deliberate, not an oversight: `AppRepository`'s own public methods return `NetworkResult<T>` where `NetworkResult` and every `T` (the model classes) are `:network`-owned types, so they're part of `:data`'s own public surface. Any consumer of `:data` needs those types resolvable on its own classpath just to use a repository's return value (e.g. `is NetworkResult.Success -> result.data`) — the same reason NIA exposes `:core:model` as `api` from `:core:data`. `implementation` would still compile if `:app` were the only consumer, since it happens to also depend on `:network` directly (for the config reasons above) — but `:feature:leaddashboard` depends on `:data` alone, with no reason to configure the network client, and calls `AppRepository.getLeadDashboard(...)` from its ViewModel: without this `api` re-export, that module would fail to resolve `NetworkResult`. This `api` re-export does **not** leak `retrofit2`/`okhttp3`/`gson` any further, though — those stay `implementation` inside `:network`'s own `build.gradle.kts`, and Gradle's `api`/`implementation` propagation only forwards a dependency that's `api` at *every* hop, so that chain dead-ends at `:network` regardless. `:data` itself has no other dependency beyond `hilt-android`/`ksp(hilt-compiler)` for its own `@Inject constructor`s — it does not depend on `okhttp`/`retrofit2`/`gson` directly, since it never builds a client or calls Gson itself.

`:network`/`:data` both depend on `hilt-android`/`ksp(hilt-compiler)` for their own `@Module`s/`@Inject constructor`s (`:network` also needs `kotlinx-coroutines-core` for the safe-call layer), but neither applies the Hilt Gradle plugin (`com.google.dagger.hilt.android`) — per Hilt's multi-module guidance, only `:app` (which has `ComposeFormApplication`, the `@HiltAndroidApp` entry point) applies that plugin; library modules just contribute `@Module`s/injectable classes via the compiler dependency. `MainActivity` is `@AndroidEntryPoint`, and `LeadDashboardViewModel`/`AcquisitionApprovalListViewModel`/`AcquisitionApprovalDetailViewModel`/`SpecificFormViewModel` are all `@HiltViewModel` and inject `AppRepository` directly, so the DI graph is exercised for real by those screens.

**Screen loading/error state**: these real screens use a flat per-screen state data class with independent fields (`LeadDashboardState`'s `isLoading`/`isRefreshing`/`isLoadingMore`/`error: String?`; `AcquisitionApprovalDetailState`'s separate `isLoading`/`reasonsLoading`/`submitting`, each with its own error field) — deliberately **not** a single sealed `UiState<T>` wrapping `Idle`/`Loading`/`Success`/`Error`. A sealed wrapper makes those states mutually exclusive, but these screens need them to coexist (e.g. `leads` staying populated while `isRefreshing = true`, or a stale error banner sitting alongside already-loaded `detail` content) - a sealed `Success`/`Error` can't represent "have data AND loading more AND the last page fetch failed" at once the way independent flags can. Follow this same shape for a new screen's state rather than introducing a generic `UiState<T>`. `AppProgressDialog` (`:designsystem`) is the blocking spinner these screens show while `isLoading`/`isRefreshing`/`submitting` is true when there's already content behind it worth protecting from interaction; `AppProgressIndicator` is the non-blocking inline spinner for a screen's very first load, before there's any content yet.

### Feature modules (`:feature:leaddashboard`, `:feature:acquisition`)

Both live under a `feature/` parent folder, nested the same way NIA nests `feature/foryou` etc. — every other module here is flat at the repo root (`:designsystem`, `:network`, `:data`, `:common`...), so `feature/` is deliberately the one grouping folder, reserved for screens that get their own module. Namespaces follow the folder: `com.touhid.composeform.feature.leaddashboard`, `com.touhid.composeform.feature.acquisition`. A future third feature would follow the identical shape: a new `feature/<name>` module depending on `:data`/`:designsystem`/`:common`, wired into `:app`'s `NavHost`.

**Dependency shape** — this is the concrete payoff of everything above: each feature module depends on `:data` (repositories), `:designsystem` (UI), and `:common` (shared helpers below) — **never `:network` directly**, and **never `:app`**. Neither needs `:network` because `:data`'s `api(project(":network"))` re-export (see above) already makes `NetworkResult`/the model types resolvable through `:data` alone — a feature module has no `@BaseUrl`/`TokenProvider` to configure, so it never needs the direct `:network` dependency `:app` keeps for that reason. Neither can depend on `:app` because that would invert the actual relationship: `:app` assembles feature modules into its `NavHost`, not the other way around. `:feature:acquisition` additionally depends on `libs.coil.compose` directly (for `AsyncImage` in its detail screen) — a dependency scoped to the one feature module that actually needs it, not shared upward.

**What had to move out of `:app` to make this work**: `common/` (`copyIconButton`, `OnEndOfListReached`, `ListEmptyState`) turned out to be used by both `leaddashboard/` and `acquisition/` — a genuinely cross-feature dependency that couldn't live inside either specific screen's module without one depending on the other. It became its own `:common` module for exactly this reason, extracted before either feature module existed; the same question (does a new feature need something `:app`-local?) is worth asking before adding a third feature module, since anything shared has to live below all of them, never inside one.

**Previews can't use `ComposeFormAppTheme`.** `:app`'s `ComposeFormAppTheme` (forces light-only at runtime) lives in `:app`, so anything living below `:app` — `:common`, `:feature:leaddashboard`, `:feature:acquisition` — can't import it (same backwards-dependency problem as above). Their own `@Preview`s use `:designsystem`'s `ComposeFormTheme` directly instead; most got both Light/Dark variants, except a few previews (e.g. `:feature:acquisition`'s bottom-sheet content previews) that hardcode a white background and so keep a single preview rather than a pointless Dark variant.

**String resources**: every UI-facing string in `:feature:leaddashboard` and `:feature:acquisition` is externalized to `res/values/strings.xml` (`stringResource(R.string.xxx)`, never a hardcoded literal in a screen/ViewModel), following NIA's own convention of prefixing every resource name with the module it lives in (`leaddashboard_*`, `acquisition_*`) so two feature modules' `strings.xml` can never collide once merged into one flat `R` namespace at APK build time - Android resources aren't Kotlin-package-namespaced the way code is. A string with the exact same wording in 2+ feature modules (confirmed by literal comparison, not assumed) lives in `:common/res/values/strings.xml` instead, prefixed `common_*` - `common_refresh`/`common_search`/`common_retry_message`/`common_retry_action`/`common_results_found_count`/`common_no_leads_found`/`common_wallet_number`/`common_address`/`common_lead_closer`/`common_serving_ma`/`common_status_approved`/`common_status_pending`/`common_status_rejected` as of this writing - so translating it once covers every screen using it, and future locale support only has one place to add a `values-<lang>/strings.xml` override for that string. A feature module reaches `:common`'s strings via `import com.touhid.composeform.common.R as CommonR` (aliased since the feature module has its own local `R` in its own package) and calls `stringResource(CommonR.string.common_xxx)` exactly like its own. A string that merely *looks* similar but isn't identical (e.g. each screen's own search placeholder wording) stays feature-local - don't force a shared entry just because the concept overlaps. An enum needing a display string (`LeadStatusFilter`) stores `@StringRes val labelRes: Int`, not a raw `label: String`, resolved via `stringResource()` at the composable call site - an enum constant isn't itself a `@Composable` context, so the string can't be resolved at declaration time. A fixed list of labels (the Likert agreement scale) is a `<string-array>`, read via `stringArrayResource()` inside the composable that uses it, not a top-level `listOf(...)` of literals. A non-composable helper that needs a resource string (e.g. a `Boolean.toYesNo()` extension) is itself annotated `@Composable` so it can call `stringResource()` - its only callers are already inside composition. Punctuation/format placeholders that aren't language content (a bare `"-"` fallback, `SimpleDateFormat` patterns, an interpolated `"$name ($id)"` built from dynamic data) are left as plain Kotlin string templates, not resource entries - resource externalization is for translatable natural-language text, not every string literal in the file.

### `:formbuilder` — JSON-driven dynamic forms

```
formbuilder/src/main/java/com/touhid/composeform/formbuilder/
├── schema/                  # FormSchema, FormField (sealed interface + 8 types), FormOption, FormInsets,
│                            # FormTextStyle, FormSize, FormOrientation, FormValue — the JSON-facing data model
├── FormSchemaParser.kt      # parseFormSchema(jsonString): FormSchema
├── FormValidator.kt         # internal validate(schema, values): Map<String, String> (field key -> error)
├── FormFieldMappers.kt      # FormTextStyle -> AppTextOverride, inputType string -> AppTextFieldType,
│                            # FormSize -> Modifier (fillMaxWidth/Height, fixed dp, or no-op for wrap_content)
├── FormState.kt             # internal FormState (values + touched), rememberSaveable via a kotlinx.serialization Saver
├── FormRenderer.kt          # public FormRenderer(schema, modifier, onSubmit) entry point
└── FormRendererPreviews.kt
```

Schema model: `FormSchema` is just `{ fields: [...] }` — **everything is a field**, including the form's title (`type: "text"`, non-interactive display) and the submit button (`type: "submit"`), positioned wherever they appear in the list. There's no separate top-level "title"/"submit" property. The 8 `type` discriminator values are `text`, `inputBox`, `checkbox`, `checkboxGroup`, `radio`, `switch`, `dropdown`, `submit`, dispatched by a `JsonContentPolymorphicSerializer` in `FormField.kt` (decode-only; `FormValue`, the submitted-data type, is separately `@Serializable` for `FormState`'s Saver round-trip, not for parsing).

Key conventions if extending the schema:
- Every field has both `margin` (space outside its bounds, separating it from neighbors) and `padding` (space inside its bounds, around its content) — distinct concepts, both `FormInsets` (`top`/`bottom`/`left`/`right` dp), both present on every field type for uniformity.
- Every field has a `size: FormSize` (`width`/`height`, each `"match_parent"` | `"wrap_content"` | a numeric dp string), defaulting to `match_parent` width / `wrap_content` height. Applied directly to the field's own rendered component (not the margin/padding wrapper `Box`s) via `FormSize.toModifier()`, since components like `AppButton`/`AppCheckbox` don't stretch on their own the way `AppTextField` does.
- Every field (and every `FormOption`) has the same `style: FormTextStyle?` (`size`/`color`/`weight`) — one property name/shape everywhere text appears, never a context-specific key like `labelStyle`/`titleStyle`.
- `radio`/`checkboxGroup`/`dropdown` share one `FormOption` model (`id`, `value`, `default`, `style`, `margin`, `padding`) — selection is tracked/returned by `id`, displayed by `value`. Each option's `margin` (zero by default, set via JSON) is what actually creates the gap between adjacent options in a group — `OptionsContainer` itself applies no arrangement spacing, so the per-option `margin` is the only knob and works symmetrically in both `orientation`s.
- `label` is optional on every field (defaults to `""`) — a field can be present purely for its side effects (e.g. a `radio`/`checkboxGroup` whose heading is supplied by a separate preceding `text` field instead of the group's own label).
- The submit button is gated: `FormRenderer` computes `validate(schema, values)` live on every recomposition and disables the button until it's empty. Per-field error text only renders once that field has been touched (tracked in `FormState`), so the button being disabled from the first frame doesn't create a dead end.
- `FormValue.Options.selected` is `List<FormValue.Option>` (just `id`/`value`), **not** `List<FormOption>` — schema metadata (`margin`/`padding`/`style`/`default`) must never leak into the submitted data. If you add a new option-bearing field type, map down to `FormValue.Option`/`FormValue.Options` the same way `checkboxGroup` does in `FormRenderer.kt` and `FormState.kt`, rather than passing the schema `FormOption` straight through.
- `visibleWhen: FormVisibilityCondition?` (`key`/`operator`/`values`) gates a field's visibility on another field's current value. `operator` is only `Equals`/`NotEquals` (no `In`) — both consult the *entire* `values` list the same way regardless of how many entries it has (`Equals`: satisfied on any overlap with the trigger's value(s); `NotEquals`: satisfied on no overlap), so there's one consistent shape rather than one that silently behaves differently depending on `values.size` (see `FormFieldVisibility.kt`). If a new operator is ever needed, give it its own full-list semantics too — never one that only inspects `values.firstOrNull()`, since a JSON author can't see that inconsistency from the schema shape alone.

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

`docs/architecture.docx` is the shareable write-up of this module architecture for people who don't need file-level detail: what each kind of module owns, the dependency rules, how features share data, navigation and build logic, with diagrams and code examples. This file (`CLAUDE.md`) stays the precise, up-to-date source of truth; the docx is a snapshot and won't be kept in sync automatically, so prefer this file when the two disagree.

## Commands

- Build everything: `./gradlew build`
- Build/check a single module: `./gradlew :app:assembleDebug`, `./gradlew :core:network:build`, `./gradlew :feature:lead:ui:build`, `./gradlew :feature:lead:domain:build` (any module path from `settings.gradle.kts` works the same way)
- Run unit tests: `./gradlew test` (single module: `./gradlew :formbuilder:testDebugUnitTest`, single test: `./gradlew :formbuilder:testDebugUnitTest --tests "com.touhid.composeform.formbuilder.FormValidatorTest"`)
- Run instrumented tests (needs a device/emulator): `./gradlew :app:connectedDebugAndroidTest`
- Lint: `./gradlew lint` (per-module: `./gradlew :app:lintDebug`)
- Install and launch on a running emulator/device:
  ```
  adb install -r app/build/outputs/apk/debug/app-debug.apk
  adb shell am start -n com.touhid.composeform/.MainActivity
  ```

## Architecture

Multi-module Gradle project organised as feature slices on top of a thin shared `core`, assembled by an `:app` shell. Shared build configuration lives in convention plugins under `build-logic/` — see "Build logic" below.

```
app/                      the shell: launcher, home + form demo, Navigator, Hilt config into :core:network
core/
  model/                  AppResult, AppError (plain Kotlin)
  network/                the HTTP client, auth + token refresh, safeApiCall
  navigation/             Destination, Navigator, DestinationHandler
  database/               Room infrastructure: buildRoomDatabase, safeDbCall (no tables)
  designsystem/           all Material3 access, the app theme
  common/                 Compose helpers and strings shared by several features
  lead/{domain,data}      core slice: lead types both features show, and their DTOs
  session/{domain,data}   core slice: sign-in
feature/
  lead/{domain,data,ui,navigation}          lead dashboard
  acquisition/{domain,data,ui,navigation}   acquisition approval list + detail/decision
  specificform/{domain,data,ui}             the server-driven "specific form" fragment
formbuilder/              JSON form schema parser + renderer, reused by features
build-logic/              convention plugins
```

Packages follow the module path, minus a `core` segment for core modules: `com.touhid.composeform.feature.lead.ui`, `com.touhid.composeform.network`, `com.touhid.composeform.lead.domain`.

**Shell**

- **`:app`** — `MainActivity.kt` (`@AndroidEntryPoint`, the launcher) hosts a `NavHost` with `home` (`home/DemoHomeScreen.kt`, picking between the demos) plus `form`/`picker` (the `flow` package's demo server-driven form flow, backed by `DemoFormApi`'s in-memory mock — not real network calls). Home opens the lead and acquisition features through the injected `Navigator` (`LeadDashboardDestination`, `AcquisitionApprovalListDestination`), never by importing their screens; `di/AppNavigator.kt` is the `Navigator` implementation (see "Navigation" below). `ComposeFormApplication.kt` is the `@HiltAndroidApp` entry point, and `di/` holds the Hilt modules `:app` owns to configure `:core:network` — the base URL, the app version code, token storage — per the deferral pattern described in "Network boundary" below. `:app` depends on every feature's `data` and `ui` module so Hilt sees their bindings and the APK merges their manifests, but only imports from `navigation` modules. It is **not permitted to depend on Material3 directly** — see "Design system boundary" below — and **not permitted to depend on Square's networking libraries directly** — see "Network boundary" below.

**Core infrastructure**

- **`:core:model`** — a plain Kotlin/JVM module holding `AppResult<T>` (`Success`/`Failure`, plus `map`) and `AppError` (`NoConnection`/`Timeout`/`Unauthorized`/`Server`/`Unknown`, each with a `message`), the result type every repository returns. Only generic types like these, never business models.
- **`:core:network`** — an Android library owning OkHttp/Retrofit and the client around it — the main `Retrofit`, auth and token refresh, interceptors, debug mocks, `safeApiCall`. It holds no feature endpoints: each `data` module declares its own. Re-exports `:core:model` via `api`, since `safeApiCall` returns `AppResult`. See "Network boundary" below.
- **`:core:database`** — an Android library holding the Room infrastructure every `data` module with local storage shares: `buildRoomDatabase` (file naming `composeform_<name>.db`, debug-only query logging) and `safeDbCall` (the database counterpart of `safeApiCall`). It holds no tables, just as `:core:network` holds no endpoints: each `data` module declares its own entities, DAOs and `@Database`. Re-exports `:core:model` and `room-runtime` via `api`. See "Local storage (Room)" below.
- **`:core:navigation`** — an Android library holding the cross-feature navigation contracts: `Destination`, `Navigator` and `DestinationHandler`. No concrete destinations; those live in each feature's `navigation` module. See "Navigation" below.
- **`:core:designsystem`** — an Android library owning all Material3-based UI, plus `ComposeFormAppTheme` (the app's theme policy). See "Design system boundary" below.
- **`:core:common`** — an Android library holding small Compose helpers and strings used by more than one feature: `copyIconButton` (a "copy to clipboard" trailing-icon slot), `LazyListState.OnEndOfListReached` (the shared infinite-scroll pagination trigger), `ListEmptyState`, `formatRejectionTimestamp`, and the `common_*` strings (see "String resources" below). Depends only on `:core:designsystem` + Compose. Anything two features share has to live below both of them like this, never inside one.

**Core slices** (`core/<topic>/{domain,data}`, no `ui`)

- **`:core:lead:{domain,data}`** — lead data both features use. `domain` (plain Kotlin/JVM) holds the value types both features show: `LeadCloser`, `Reviewer`, `Rejection`, `RejectionReason`. `data` (plain Kotlin/JVM) holds their wire DTOs (`LeadCloserDto`, `ReviewerDto`, `RejectionDto`, `RejectionReasonDto`) and `toDomain()` mappers, which both features' responses embed; only the two feature `data` modules depend on it.
- **`:core:session:{domain,data}`** — sign-in. `domain` (plain Kotlin/JVM) holds `SessionRepository.login(...)` returning `AppResult<UserSession>`; `data` holds `SessionApi` (`POST v1/login`), its DTOs and `SessionRepositoryImpl`, which stores the access/refresh tokens through `:core:network`'s `TokenProvider`. A core slice rather than a feature because signing in (and later out) is needed by more than one feature. Nothing calls it yet; there is no sign-in screen.

**Feature slices** (`feature/<name>/{domain,data,ui,navigation}` — see "Feature slices" below for the shape)

- **`:feature:lead`** — the lead dashboard. `ui` holds `LeadDashboardScreen.kt`, `LeadDashboardViewModel.kt` (`@HiltViewModel`, injects `LeadRepository`), `LeadDashboardModels.kt` (the screen-local `LeadStatusFilter` enum), `LeadActivity.kt` (the host Activity), `LeadNavigation.kt` (its `DestinationHandler`) and `EkycVerificationActivity.kt`. `navigation` holds `LeadDashboardDestination`. `data` holds `LeadApi`, `LeadDtos.kt`, `LeadMappers.kt`, `LeadRepositoryImpl`, `LeadDataModule`.
- **`:feature:acquisition`** — the acquisition approval list + detail/decision flow. `ui` holds `AcquisitionApprovalListScreen.kt`/`AcquisitionApprovalListViewModel.kt` and `AcquisitionApprovalDetailScreen.kt`/`AcquisitionApprovalDetailViewModel.kt` (both `@HiltViewModel`, injecting `AcquisitionRepository`), plus `AcquisitionActivity.kt` (the host Activity, whose `NavHost` routes list -> detail) and `AcquisitionNavigation.kt` (its `DestinationHandler`). It also depends on Coil (`libs.coil.compose`) for `AsyncImage` in the detail screen — the only module that needs it. `navigation` holds `AcquisitionApprovalListDestination`. `data` mirrors lead's files (`AcquisitionApi`, `AcquisitionDtos.kt`, `AcquisitionMappers.kt`, `AcquisitionRepositoryImpl`, `AcquisitionDataModule`).
- **`:feature:specificform`** — the server-driven "specific form" screen. `ui` holds `SpecificFormFragment` (not wired into any host yet; meant to be one step of a host Activity's form wizard) and `SpecificFormViewModel` (injects `SpecificFormRepository`, renders the schema with `:formbuilder`, and on submit uploads the answers through `SpecificFormRepository.submit` - `POST v1/forms/specific/submit`, mocked like the form itself - showing `AppProgressDialog` while it runs and a success or Retry snackbar after). A `FormSubmission` carries the form's key and its answers as question key -> answer, with option answers as the option's key rather than its display text. The domain's `SpecificForm.schemaJson` is the `{"questions": [...]}` string `parseSpecificFormSchema` reads, so no JSON library type reaches the ui. No `navigation` module, since nothing outside the feature opens it.

**Libraries**

- **`:formbuilder`** — an Android library that parses a JSON form schema (`kotlinx.serialization`) and renders it using `:core:designsystem`'s components. Also subject to the Material3-free boundary. See "`:formbuilder` — JSON-driven dynamic forms" below.

### Build logic (convention plugins)

New to convention plugins? [`build-logic/README.md`](build-logic/README.md) explains the module from scratch: what each class does, which plugin a new module should use, and the common changes. `build-logic/` is an included build (`pluginManagement { includeBuild("build-logic") }` in `settings.gradle.kts`) holding the shared Gradle setup as convention plugins, so a module's `build.gradle.kts` states only its namespace and what is specific to it. SDK levels and the Java version live in one place, `ProjectConfig` in `build-logic/convention/src/main/kotlin/ProjectExtensions.kt` — change `compileSdk`/`minSdk`/`targetSdk`/Java version there, never in a module.

| Plugin id | Applies | Used by |
| --- | --- | --- |
| `composeform.android.application` | `com.android.application` + Compose compiler, SDK levels, Java 11, `buildFeatures.compose`, Compose BOM + `ui`/`foundation`/`ui-tooling-preview` (+ `ui-tooling` for debug) | `:app` |
| `composeform.android.library` | `com.android.library`, SDK levels, Java 11 | `:core:network`, `:core:navigation`, `:core:database`, `:core:session:data`, every feature's `data` and `navigation` |
| `composeform.android.library.compose` | `composeform.android.library` + Compose compiler, `buildFeatures.compose`, the same Compose dependencies | `:core:designsystem`, `:formbuilder`, `:core:common` |
| `composeform.hilt` | KSP + `hilt-android` + `hilt-compiler` (not the Hilt Gradle plugin — only `:app` applies that, per Hilt's multi-module guidance) | `:app`, `:core:network`, `:core:session:data`, feature `data` and `ui` modules |
| `composeform.android.feature` | `composeform.android.library.compose` + `composeform.hilt`, `:core:designsystem`, `:core:common`, `material-icons-extended`, lifecycle ViewModel/runtime Compose, `hilt-navigation-compose` | every feature's `ui` module |
| `composeform.android.room` | KSP + `room-runtime`/`room-ktx`/`ksp(room-compiler)`, schema export to the module's `schemas/`, `:core:database` | a `data` module with its own Room database (none yet), on top of `composeform.android.library` + `composeform.hilt` |
| `composeform.jvm.library` | `org.jetbrains.kotlin.jvm`, Java/Kotlin JVM target from `ProjectConfig` | `:core:model`, `:core:lead:domain`, `:core:lead:data`, `:core:session:domain`, every feature's `domain` |
| `composeform.dependency.rules` | Fails the build on a forbidden project dependency (see "Dependency rules" below) | applied by `composeform.android.application`, `composeform.android.library` and `composeform.jvm.library`, so every module |

The plugins depend on AGP as `compileOnly` (`libs.android.gradlePlugin`): the root `build.gradle.kts` already puts AGP, KSP and the Compose compiler on the build classpath with `apply false`, and the plugins apply them by id. Keep those `apply false` entries — removing one makes the matching convention plugin fail to apply. Adding a module: pick the one plugin that matches its kind, then add only its own dependencies. `build-logic`'s own `clean` is deliberately a no-op (see `build-logic/convention/build.gradle.kts`): without that, Android Studio's "Clean and Assemble Project with Tests"/"Rebuild" deadlocks with "Unable to make progress running work", because it cleans the plugin jar the same invocation already loaded.

### Design system boundary (important, easy to violate accidentally)

`:core:designsystem` is the only module that depends on `androidx.compose.material3`, and as `implementation` (not `api`). The Compose convention plugins give every other Compose module `ui`/`foundation`/`ui-tooling-preview` but never Material3, so Material3 classes are not on their compile classpaths at all — any `import androidx.compose.material3.*` added in `:app`, `:formbuilder`, `:core:common` or a feature `ui` module will fail to compile. This is deliberate, compiler-enforced encapsulation: all UI must go through `:core:designsystem`'s wrapped components (`AppText`, `AppButton`, `AppScaffold`, etc.), never the raw Material3 APIs. (Foundation layout primitives — `Column`/`Row`/`Box`/`Modifier.padding` — are fine for any module to use directly; only Material3 is restricted. This includes `Image` — `androidx.compose.foundation.Image` (and Coil's `AsyncImage`, used by `:feature:acquisition:ui`'s detail screen) is Foundation, not Material3, so any module can call it directly with no `AppImage` wrapper needed; `Icon` is the one that's Material3-gated and needs `AppIcon`.)

When a module needs a new Material3 primitive it doesn't have a wrapper for yet, add the wrapper to `:core:designsystem` rather than adding a direct dependency elsewhere.

Components are organized by category (not a flat package) — when adding a new component, put it under the matching category subpackage, creating a new one if it doesn't fit an existing one.

Conventions established by existing components:
- Each component wraps a Material3 equivalent with a narrowed, opinionated API (e.g. `AppTextStyle` enum instead of raw `TextStyle` passthrough) — don't leak Material3/Foundation types (like `PaddingValues`) through a component's public signature if avoidable (see `AppScaffold`: it absorbs `innerPadding` internally via a `Box` rather than exposing it). A container component's `content` slot should still be typed with that container's actual scope (`AppCard`'s is `ColumnScope`, `AppBottomActionBar`'s is `RowScope`, `AppScaffold`'s is `BoxScope`) — the scope isn't a Material3/Foundation type worth hiding, and exposing the wrong one (or none) either silently breaks `weight`/`align` modifiers at runtime or blocks them outright.
- Every component that renders text accepts an optional `AppTextOverride` (`fontSize`/`fontWeight`/`color`, all no-op by default) — `AppText`'s `override`, `AppButton`/`AppOutlinedButton`'s `textOverride`, `AppCheckbox`/`AppRadioButton`/`AppSwitch`/`AppDropdown`'s `labelOverride`. This is how callers (like `:formbuilder`) apply per-instance styling without the design system losing its opinionated defaults.
- Spacing between elements inside a component uses `AppSpacing` (`theme/Spacing.kt`) tokens, not hardcoded `dp` values.
- Each category subpackage has its own `*Previews.kt` file (not one global previews file) with a private composable carrying stacked `@Preview(name = "Light", ...)` / `@Preview(name = "Dark", uiMode = Configuration.UI_MODE_NIGHT_YES, ...)` annotations, wrapped in `ComposeFormTheme`.
- Modules outside `:core:designsystem` (e.g. `:app`) can reference `ImageVector` constants from `androidx.compose.material:material-icons-core` (or its superset, `material-icons-extended` — `:app` uses the extended artifact since it needs glyphs like `ContentCopy` outside the curated core set; both are separate artifacts with no Material3 dependency) directly and pass them into a designsystem component (`AppIcon`, `AppIconButton`, `AppTopBarAction`, `AppButton`'s `leadingIcon` slot, etc.) — but any `@Composable` slot lambda a caller *writes* (e.g. `AppIconLabelValue`'s `icon` param) still compiles as part of that caller's own module, so its body must only call designsystem-exposed composables (`AppIcon`, not raw Material3 `Icon`), never Material3 directly.
- Not everything a screen renders belongs in `:core:designsystem`, even when it's visually involved and looks reusable in principle. The boundary's purpose is specifically wrapping Material3 access `:app`/`:formbuilder` can't otherwise reach — a composition already buildable from exposed primitives (`AppText`, `AppIcon`, Foundation `Row`/`Column`/`Box`/`border`/`background`) has no Material3-wrapping reason to move, and "some other screen might want this shape someday" isn't a reason either - that's the same speculative-reuse trap the rest of this doc argues against for ordinary code. Ask two concrete questions instead of a hypothetical one: (1) does it have an *actual* second caller today, not an imagined future one? (2) does it use a Material3-derived default (`MaterialTheme.colorScheme...`) that its real caller(s) actually rely on, rather than always overriding? `AcquisitionApprovalDetailScreen`'s score-band step indicator and its score circle both answer no to both - one caller, always-explicit colors - so both live in their own feature module (`:feature:acquisition:ui`), built from `AppText`/`AppIcon`/`AppTextOverride` plus plain Foundation shapes.

### Network boundary (same pattern as the design system boundary)

`:core:network` depends on `okhttp` (+ `logging-interceptor`) and `retrofit2` (+ `converter-scalars`, `converter-gson`) as `implementation` (not `api`). It owns the HTTP client and everything around it — auth, token refresh, error mapping, logging, debug mocks — but no endpoints of its own except the token refresh. Each feature's (or core slice's) `data` module declares its own Retrofit interface and DTOs, creates the service from `:core:network`'s main `Retrofit`, and calls it through `safeApiCall`; it declares `retrofit2`/`gson` itself as `implementation`, so they never reach a `ui` module or `:app`. Only `data` modules (and `:app`, to configure it) may depend on `:core:network` — the dependency-rules plugin enforces this.

`:core:network` is organized into subpackages by category, the same spirit as `:core:designsystem`'s: `api/` (`RefreshTokenApiService` only), `model/` (its request/response classes), `auth/` (`TokenProvider`/`AuthInterceptor`/`TokenAuthenticator`/`AuthSessionEvents`, kept together since they're auth-domain-specific rather than grouped by "interceptor" shape), `interceptor/` (the other, non-auth, non-mock interceptors — `RequestIdInterceptor`/`AppVersionInterceptor`/`ErrorInterceptor`), `mock/` (`MockDataInterceptor`/`MockJson` — temporary scaffolding for the still-nonexistent backend, deleted together once a real backend exists), and `qualifier/` (`@BaseUrl` and `@AppVersionCode`, plus the internal `@RefreshRetrofit`). `RetrofitFactory`, `NetworkModule` and `SafeApiCall.kt` stay at the package root since they're cross-cutting.

- `@BaseUrl` (`core/network/.../qualifier/BaseUrl.kt`) — a Hilt qualifier `:app` binds to a `String` (`di/AppNetworkModule.kt`) so `:core:network` never hardcodes an environment's base URL. Retrofit requires a trailing slash (`https://api.example.com/`, not `.../com`) — `RetrofitFactory` normalizes a missing one, but supply it correctly regardless. Once product flavors exist, `:app` reads this from a per-flavor `BuildConfig.BASE_URL` — `:core:network` itself never needs to know about flavors. Today `:app` reads it from the injected `SharedPreferences` (see `di/AppPreferencesModule.kt` below), once per process at Hilt's `SingletonComponent` resolution, so a value saved later only takes effect on the next app restart; it falls back to the placeholder `https://api.composeform.dummy/` when unset or blank (nothing writes the key yet). Never let that fallback be `""`: `RetrofitFactory` normalizes it to `"/"`, which `Retrofit.Builder().baseUrl()` rejects with "Expected URL scheme 'http' or 'https'" the first time any repository is injected — usually surfacing at `@RefreshRetrofit`, only because Hilt builds it first (`TokenAuthenticator` depends on it). In debug builds `MockDataInterceptor` answers mocked paths regardless of host, so the placeholder is enough to run the app.
- The main `Retrofit` (unqualified, `NetworkModule.provideRetrofit`) — the client every `data` module creates its service from (`retrofit.create(LeadApi::class.java)` in its own Hilt module), so every endpoint shares the same auth, token refresh, error mapping and debug mocks. When a second, unrelated backend appears, give it its own public `@XBaseUrl` qualifier, an internal `@XRetrofit` qualifier and a `@Provides` in `NetworkModule` calling `RetrofitFactory.create()` with exactly the interceptors it needs (e.g. `authInterceptor = null` for a third-party backend that must never see our bearer token) — never reuse `@BaseUrl` for it.
- `safeApiCall` (`core/network/.../SafeApiCall.kt`) — the one public safe-call entry point: runs a suspending Retrofit call on `Dispatchers.IO` and returns `:core:model`'s `AppResult` (`Success`, or `Failure(AppError.NoConnection|Timeout|Unauthorized|Server|Unknown)`). It maps `ErrorInterceptor`'s `ApiException`/`HttpException`/`SocketTimeoutException`/`IOException`/anything else straight into `AppError`: HTTP 401 → `Unauthorized`, any other HTTP status → `Server(code, status, message)`, timeout → `Timeout`, other I/O failures → `NoConnection`, the rest → `Unknown`. `retrofit2`/`okhttp3`/`java.io` exception types never cross the `:core:network` boundary, same spirit as not leaking Material3 types from `:core:designsystem`. `CancellationException` is rethrown, not wrapped. `ApiException` is caught ahead of the generic `IOException` branch (it's an `IOException` subtype itself) since otherwise it would fall through to `NoConnection`; it maps onto the same `AppError` a plain `HttpException` would, just with the backend's own `message`/`status` instead of the generic HTTP reason phrase.
- `ErrorInterceptor` (`core/network/.../interceptor/ErrorInterceptor.kt`) — `internal`. Error detection stays purely HTTP-status-based (`!response.isSuccessful`) — a body field like the app API's `is_error` was considered and rejected as the signal, since it isn't a reliable discriminator on this backend. What the interceptor actually does is enrich a non-2xx response: it reads the error body's own `{message, status}` (via `peekBody`, so the real Retrofit converter still reads the original untouched body) and throws `ApiException(code, status, rawBody, message)` carrying them, instead of letting a bare `HttpException`'s generic reason-phrase message reach `safeApiCall`. Read defensively — a body that isn't valid JSON, or lacks those fields, falls back to the HTTP reason phrase rather than failing a second way. Scoped to just the main `@BaseUrl` client in `NetworkModule` (passed through `RetrofitFactory.create()`'s `interceptors` list, not added unconditionally like `RequestIdInterceptor`) since this error-body shape is this backend's own, not something another backend added later is guaranteed to share.
- `core/network/.../auth/` — `TokenProvider` (the contract; storage is deferred to the consuming module, same pattern as `@BaseUrl`) and `AuthInterceptor` (`internal`, attaches `Authorization: Bearer <token>` when a token is present), plus the refresh-token mechanism: `login` returns a `refreshToken` alongside the access `token`, and `:core:session:data`'s `SessionRepositoryImpl` stores both via `TokenProvider` (which now also has `getRefreshToken`/`setRefreshToken`/`clear`). `TokenAuthenticator` (`internal`, an OkHttp `Authenticator`) is attached to the main `@BaseUrl` client only (via `RetrofitFactory.create()`'s optional `authenticator` param): on a 401 for a request that carried a token, it calls `RefreshTokenApiService` (`POST v1/auth/refresh`, a blocking `Call<T>` since authenticators run synchronously) and retries once with the new token and a fresh `X-Request-Id`. The refresh is `synchronized` and skipped if another request already rotated the token, so parallel 401s trigger one refresh. `RefreshTokenApiService` is served by its own `@RefreshRetrofit` (same base URL, no `AuthInterceptor`, no authenticator) so the refresh call can never recurse into the authenticator. A missing refresh token or a 401/403 from the refresh endpoint ends the session — `TokenProvider.clear()` plus an emission on `AuthSessionEvents.sessionExpired` (public, `@Singleton`, a `SharedFlow<Unit>`) — and what happens next (navigating to sign-in) is `:app`'s concern; nothing collects it yet since no sign-in screen exists. Connectivity failures and 5xx from the refresh endpoint keep the session and just surface the original 401. `:app` binds `TokenProvider` to `di/EncryptedTokenProvider.kt` (backed by `androidx.security.crypto.EncryptedSharedPreferences`, so the token survives app relaunch) via `di/AppTokenModule.kt`. `EncryptedTokenProvider` doesn't build its own `EncryptedSharedPreferences` instance — it injects the plain `SharedPreferences` type, resolved to the one shared instance `di/AppPreferencesModule.kt` provides (file `"app_prefs"`). That same instance is also where `AppNetworkModule.kt` reads the base URL — one encrypted store for the whole app's local preferences, not one file per concern. Deliberate: `EncryptedSharedPreferences` encrypts every entry in a given file uniformly (no way to mix plain and encrypted entries within one file), so consolidating means non-secret values like base URLs pay the same `MasterKey`/crypto overhead the token needs - accepted in exchange for one shared store other app-local settings can keep growing into, rather than a new dedicated file per setting. `:core:session:data`'s `SessionRepositoryImpl` also depends on `TokenProvider` directly (to store the tokens on a successful login), so `TokenProvider` stays public.
- `RetrofitFactory` (`core/network/.../RetrofitFactory.kt`) — `internal`, the one place that actually builds an `OkHttpClient`/`Retrofit` pair: `create(baseUrl, authInterceptor: Interceptor?, interceptors: List<Interceptor> = emptyList(), authenticator: Authenticator? = null)`. Each client is built with exactly the interceptors it needs — `authInterceptor` is nullable so a client that must never carry this app's bearer token omits it entirely; `interceptors` covers anything else one client needs without every other client paying for it. `RequestIdInterceptor` (`X-Request-Id: UUID.randomUUID()`, regenerated per request inside `intercept()`) and `AppVersionInterceptor` (`X-Version: android/<versionCode>`) are added to every client unconditionally. The version code comes from `@AppVersionCode`, which `:app` binds to its own `BuildConfig.VERSION_CODE` in `di/AppNetworkModule.kt` (library modules have no version code; `:app` enables `buildFeatures.buildConfig` for this). Interceptor order matters for one of them: the debug-only `MockDataInterceptor` is added **last**, after `loggingInterceptor`, because it answers a mocked path without calling `chain.proceed()` - anything added after it never runs, which is exactly how OkHttp logging once silently vanished from logcat when it sat first. Last in the chain, it stands in for just the network transport.
- `NetworkModule` (`core/network/.../NetworkModule.kt`) — `internal`, provides the shared `HttpLoggingInterceptor` (debug-gated: `Level.BODY` only when `:core:network`'s own generated `BuildConfig.DEBUG` is true, `Level.NONE` otherwise so release builds never log request/response bodies), the main `Retrofit`, and the `@RefreshRetrofit`/`RefreshTokenApiService` pair. `:core:network` enables `buildFeatures.buildConfig` itself for this — deliberately not a Hilt qualifier like `@BaseUrl`, since Gradle's variant-aware dependency resolution already gives every module the `BuildConfig.DEBUG` matching whichever build type of `:app` is being built.

### Local storage (Room)

Same split as the network: `:core:database` provides the shared infrastructure, and each `data` module that stores data locally owns its tables. That module applies `composeform.android.room` and declares, all `internal`, its entities, DAOs and **one** `@Database` listing them (Room needs every entity of a database at compile time, so a shared database in core would have to import feature types). Its Hilt module provides the database with `buildRoomDatabase(context, XDatabase::class.java, "<name>").addMigrations(...).build()` as `@Singleton`, plus each DAO; the repository wraps writes in `safeDbCall` and exposes observing reads as `Flow`. A second table goes into that same `@Database`, never a second database in the same module. Tables two features need live in a core slice's `data` module, same rule as any shared data. Commit each module's `schemas/` folder; every `version` bump needs a migration, never `fallbackToDestructiveMigration` in release. Only `data` modules may depend on `:core:database` (`:app` included in the ban: it has nothing to configure there).

**Hilt across modules**: library modules (`:core:network`, every `data` and `ui` module) depend on `hilt-android`/`ksp(hilt-compiler)` through `composeform.hilt` for their own `@Module`s/`@Inject constructor`s, but none applies the Hilt Gradle plugin (`com.google.dagger.hilt.android`) — per Hilt's multi-module guidance, only `:app` (which has `ComposeFormApplication`, the `@HiltAndroidApp` entry point) applies it. That's why `:app` depends on every `data` module even though it never imports from them: Hilt must see their binding modules when it builds the app's component. Repositories are interfaces in `domain`, bound to their `internal` implementations with `@Binds` in the `data` module, so a ViewModel test can substitute a fake. `MainActivity` and the feature host Activities are `@AndroidEntryPoint`; `LeadDashboardViewModel` injects `LeadRepository`, the two acquisition ViewModels inject `AcquisitionRepository`, and `SpecificFormViewModel` injects `SpecificFormRepository` (all `@HiltViewModel`).

### Dependency rules (enforced by `composeform.dependency.rules`)

`build-logic`'s `DependencyRulesPlugin` is applied by the application, Android library and JVM library convention plugins, so every module gets it. It fails the build at configuration time, naming the offending `from -> to` pair, when a project dependency breaks one of these rules (`build-logic/README.md` has the same list, plus how the plugin classifies modules by path):

- Nothing depends on `:app`.
- Only `:app` and feature modules depend on a feature module, and a feature depends on another feature only through its `navigation` module.
- Only `data` modules (and `:app`) depend on `:core:network`.
- Only `data` modules depend on `:core:database` (not even `:app`).
- A `domain` module depends only on `:core:model` and core-slice `domain` modules.
- A `navigation` module depends only on `:core:navigation`.
- A `ui` module never depends on a `data` module (its own or a core slice's).
- A `data` module never depends on a `ui` or `navigation` module.

Shared data moves into a core slice (`:core:<topic>:{domain,data}`) once a second feature needs it — never into another feature.

### Feature slices

A feature is a business area, not a screen: `feature/<name>/` holds up to four modules, and `:feature:lead:ui` could hold twenty lead screens.

- **`domain`** (`composeform.jvm.library`, plain Kotlin) — the feature's models and repository interfaces, returning `AppResult` from `:core:model`. Models are shaped for the app, not the wire. ViewModels call repositories directly; a use case is written only to combine repositories, or for a business rule more than one ViewModel applies.
- **`data`** (`composeform.android.library` + `composeform.hilt`) — its own Retrofit interface, wire DTOs and `toDomain()` mappers, all `internal`, plus the `internal` repository implementation (calls go through `:core:network`'s `safeApiCall`) and a Hilt module that binds the repository and creates the API from `:core:network`'s main `Retrofit`. Declares Retrofit/Gson itself as `implementation`.
- **`ui`** (`composeform.android.feature`) — screens (`internal`), ViewModels, strings, the feature's host Activity and its `DestinationHandler`s, with its own `AndroidManifest.xml`. Depends on its own `domain` and `navigation`, plus `:core:designsystem`/`:core:common` (added by the plugin) — never on any `data` module or `:core:network`.
- **`navigation`** (`composeform.android.library`) — only once another module needs to open the feature's screens: its `Destination`s (and later, result contracts). The only module of a feature anything outside it may depend on.

A feature never depends on another feature's `domain`, `data` or `ui`. When a second feature needs data a feature owns, its `domain` and `data` parts move into a core slice (`core/<topic>/{domain,data}`, named after the topic, never `core:shared`) and no copy stays behind — that's how `:core:lead` came about. The dependency-rules plugin enforces all of this (see "Dependency rules" above).

**Adding a feature**: create `feature/<name>/{domain,data,ui}` with one convention plugin each, `include` them in `settings.gradle.kts`, add `implementation(project(...))` for `data` and `ui` to `:app` (Hilt and manifest merging need them), and add a `navigation` module once anything outside the feature opens it.

**Screen loading/error state**: these real screens use a flat per-screen state data class with independent fields (`LeadDashboardState`'s `isLoading`/`isRefreshing`/`isLoadingMore`/`error: String?`; `AcquisitionApprovalDetailState`'s separate `isLoading`/`reasonsLoading`/`submitting`, each with its own error field) — deliberately **not** a single sealed `UiState<T>` wrapping `Idle`/`Loading`/`Success`/`Error`. A sealed wrapper makes those states mutually exclusive, but these screens need them to coexist (e.g. `leads` staying populated while `isRefreshing = true`, or a stale error banner sitting alongside already-loaded `detail` content) - a sealed `Success`/`Error` can't represent "have data AND loading more AND the last page fetch failed" at once the way independent flags can. Follow this same shape for a new screen's state rather than introducing a generic `UiState<T>`. `AppProgressDialog` (`:core:designsystem`) is the blocking spinner these screens show while `isLoading`/`isRefreshing`/`submitting` is true when there's already content behind it worth protecting from interaction; `AppProgressIndicator` is the non-blocking inline spinner for a screen's very first load, before there's any content yet.

**Theme: `ComposeFormAppTheme` for every Activity/Fragment, `ComposeFormTheme` for previews.** `ComposeFormAppTheme` (`:core:designsystem`'s `theme/AppTheme.kt`) is the app's current policy, light-only regardless of system dark mode or dynamic color; every Activity's and Fragment's `setContent` uses it (`MainActivity`, `LeadActivity`, `EkycVerificationActivity`, `AcquisitionActivity`, `SpecificFormFragment`). It lives in `:core:designsystem` rather than `:app` because the Activities now live in feature modules, which can't depend on `:app`. `@Preview`s use `ComposeFormTheme` directly instead, so their Light/Dark pairs still follow each preview's `uiMode`; a few previews (e.g. `:feature:acquisition:ui`'s bottom-sheet content previews) hardcode a white background and so keep a single preview rather than a pointless Dark variant.

**Navigation**: a module opens another feature's screen only through `:core:navigation` — `navigator.navigate(SomeDestination)`. `Destination`s are declared in the owning feature's `navigation` module (Android libraries, since cross-feature result contracts will need Android types too), the only module of a feature another module may depend on. The owning feature's `ui` registers a `DestinationHandler` per destination (`@Binds @IntoSet` in a `SingletonComponent` module, e.g. `LeadNavigation.kt`), which starts that feature's host Activity; `:app`'s `AppNavigator` (bound in `ActivityComponent`, using the Activity context) collects the set and dispatches by destination type. Navigation *inside* a feature stays the feature's own choice (`AcquisitionActivity`'s `NavHost` with string routes for list -> detail). ViewModels never navigate; they expose state/events and the Activity or composable calls `navigate()`. Feature screens are `internal`: only the feature's own host Activity renders them.

**Host Activities and manifests**: each feature `ui` module declares its own Activities in its own `src/main/AndroidManifest.xml` (relative names resolved against its namespace, no `android:theme` so they inherit `:app`'s `<application>` theme); `:app`'s manifest lists only `MainActivity`. Because only `:app` applies the Hilt Gradle plugin, feature Activities/Fragments use the long Hilt form — `@AndroidEntryPoint(ComponentActivity::class) class LeadActivity : Hilt_LeadActivity()` — since the short form (`: ComponentActivity()`) relies on that plugin's bytecode rewrite. `EkycVerificationActivity` (a dummy placeholder for a real eKYC verification SDK, launched via `ActivityResultContracts.StartActivityForResult` from `LeadDashboardScreen`) needs no Hilt and is registered in `:feature:lead:ui`'s manifest.

**String resources**: every UI-facing string in `:feature:lead:ui` and `:feature:acquisition:ui` is externalized to `res/values/strings.xml` (`stringResource(R.string.xxx)`, never a hardcoded literal in a screen/ViewModel), following NIA's own convention of prefixing every resource name with the module it lives in (`leaddashboard_*`, `acquisition_*`) so two feature modules' `strings.xml` can never collide once merged into one flat `R` namespace at APK build time - Android resources aren't Kotlin-package-namespaced the way code is. A string with the exact same wording in 2+ feature modules (confirmed by literal comparison, not assumed) lives in `:core:common/res/values/strings.xml` instead, prefixed `common_*` - `common_refresh`/`common_search`/`common_retry_message`/`common_retry_action`/`common_results_found_count`/`common_no_leads_found`/`common_wallet_number`/`common_address`/`common_lead_closer`/`common_serving_ma`/`common_status_approved`/`common_status_pending`/`common_status_rejected`/`common_status_unknown`/`common_reviewer_label` as of this writing - so translating it once covers every screen using it, and future locale support only has one place to add a `values-<lang>/strings.xml` override for that string. A feature module reaches `:core:common`'s strings via `import com.touhid.composeform.common.R as CommonR` (aliased since the feature module has its own local `R` in its own package) and calls `stringResource(CommonR.string.common_xxx)` exactly like its own. A string that merely *looks* similar but isn't identical (e.g. each screen's own search placeholder wording) stays feature-local - don't force a shared entry just because the concept overlaps. An enum needing a display string (`LeadStatusFilter`) stores `@StringRes val labelRes: Int`, not a raw `label: String`, resolved via `stringResource()` at the composable call site - an enum constant isn't itself a `@Composable` context, so the string can't be resolved at declaration time. A fixed list of labels (the Likert agreement scale) is a `<string-array>`, read via `stringArrayResource()` inside the composable that uses it, not a top-level `listOf(...)` of literals. A non-composable helper that needs a resource string (e.g. a `Boolean.toYesNo()` extension) is itself annotated `@Composable` so it can call `stringResource()` - its only callers are already inside composition. Punctuation/format placeholders that aren't language content (a bare `"-"` fallback, `SimpleDateFormat` patterns, an interpolated `"$name ($id)"` built from dynamic data) are left as plain Kotlin string templates, not resource entries - resource externalization is for translatable natural-language text, not every string literal in the file.

### `:formbuilder` — JSON-driven dynamic forms

```
formbuilder/src/main/java/com/touhid/composeform/formbuilder/
├── schema/                  # FormSchema, FormField (sealed interface + 8 types), FormOption, FormInsets,
│                            # FormTextStyle, FormSize, FormOrientation, FormValue — the JSON-facing data model
├── FormSchemaParser.kt      # parseFormSchema(jsonString): FormSchema
├── FormValidator.kt         # internal validate(schema, values): Map<String, String> (field key -> error)
├── FormFieldMappers.kt      # FormTextStyle -> AppTextOverride, inputType string -> AppTextFieldType,
│                            # FormSize -> Modifier (fillMaxWidth/Height, fixed dp, or no-op for wrap_content)
├── FormState.kt             # internal FormState (values + touched), rememberSaveable via a kotlinx.serialization Saver
├── FormRenderer.kt          # public FormRenderer(schema, modifier, onSubmit) entry point
└── FormRendererPreviews.kt
```

Schema model: `FormSchema` is just `{ fields: [...] }` — **everything is a field**, including the form's title (`type: "text"`, non-interactive display) and the submit button (`type: "submit"`), positioned wherever they appear in the list. There's no separate top-level "title"/"submit" property. The 8 `type` discriminator values are `text`, `inputBox`, `checkbox`, `checkboxGroup`, `radio`, `switch`, `dropdown`, `submit`, dispatched by a `JsonContentPolymorphicSerializer` in `FormField.kt` (decode-only; `FormValue`, the submitted-data type, is separately `@Serializable` for `FormState`'s Saver round-trip, not for parsing).

Key conventions if extending the schema:
- Every field has both `margin` (space outside its bounds, separating it from neighbors) and `padding` (space inside its bounds, around its content) — distinct concepts, both `FormInsets` (`top`/`bottom`/`left`/`right` dp), both present on every field type for uniformity.
- Every field has a `size: FormSize` (`width`/`height`, each `"match_parent"` | `"wrap_content"` | a numeric dp string), defaulting to `match_parent` width / `wrap_content` height. Applied directly to the field's own rendered component (not the margin/padding wrapper `Box`s) via `FormSize.toModifier()`, since components like `AppButton`/`AppCheckbox` don't stretch on their own the way `AppTextField` does.
- Every field (and every `FormOption`) has the same `style: FormTextStyle?` (`size`/`color`/`weight`) — one property name/shape everywhere text appears, never a context-specific key like `labelStyle`/`titleStyle`.
- `radio`/`checkboxGroup`/`dropdown` share one `FormOption` model (`id`, `value`, `default`, `style`, `margin`, `padding`) — selection is tracked/returned by `id`, displayed by `value`. Each option's `margin` (zero by default, set via JSON) is what actually creates the gap between adjacent options in a group — `OptionsContainer` itself applies no arrangement spacing, so the per-option `margin` is the only knob and works symmetrically in both `orientation`s.
- `label` is optional on every field (defaults to `""`) — a field can be present purely for its side effects (e.g. a `radio`/`checkboxGroup` whose heading is supplied by a separate preceding `text` field instead of the group's own label).
- The submit button is gated: `FormRenderer` computes `validate(schema, values)` live on every recomposition and disables the button until it's empty. Per-field error text only renders once that field has been touched (tracked in `FormState`), so the button being disabled from the first frame doesn't create a dead end.
- `FormValue.Options.selected` is `List<FormValue.Option>` (just `id`/`value`), **not** `List<FormOption>` — schema metadata (`margin`/`padding`/`style`/`default`) must never leak into the submitted data. If you add a new option-bearing field type, map down to `FormValue.Option`/`FormValue.Options` the same way `checkboxGroup` does in `FormRenderer.kt` and `FormState.kt`, rather than passing the schema `FormOption` straight through.
- `visibleWhen: FormVisibilityCondition?` (`key`/`operator`/`values`) gates a field's visibility on another field's current value. `operator` is only `Equals`/`NotEquals` (no `In`) — both consult the *entire* `values` list the same way regardless of how many entries it has (`Equals`: satisfied on any overlap with the trigger's value(s); `NotEquals`: satisfied on no overlap), so there's one consistent shape rather than one that silently behaves differently depending on `values.size` (see `FormFieldVisibility.kt`). If a new operator is ever needed, give it its own full-list semantics too — never one that only inspects `values.firstOrNull()`, since a JSON author can't see that inconsistency from the schema shape alone.
